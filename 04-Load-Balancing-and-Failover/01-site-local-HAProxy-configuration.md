# **4.1 Lab: Configuring the Site-Local HAProxy**
##### (v26.2/v26.6 Production-Hardened Guide)

In this section, we will configure the HAProxy server for **Site A**. The steps for **Site B** are identical, simply replacing the local hostnames and IP addresses.

---

### **Step 1: Install HAProxy**

Log in to your `sso-lb-a` VM and install the HAProxy package from the standard RHEL 9 repositories:

```sh
sudo dnf install haproxy -y
```

---

### **Step 2: Configure the Firewall**

We must allow public HTTPS traffic to reach our new load balancer on the standard port `443`:

```sh
# Allow traffic on the standard HTTPS port
sudo firewall-cmd --permanent --add-service=https
sudo firewall-cmd --reload
```

---

### **Step 3: Configure SELinux**

By default, SELinux prevents HAProxy (which runs as a confined system daemon) from establishing outgoing connections to non-standard ports. Since our Keycloak metrics and health checkpoints listen on port `9000` (non-standard), SELinux will block HAProxy's health checking probes.

Enforce the following persistent SELinux boolean to grant HAProxy the required network access:

```sh
# Allow HAProxy to connect to backend network ports
sudo setsebool -P haproxy_connect_any 1
```

---

### **Step 4: Deploy the TLS Certificate**

As established in our prerequisites, this load balancer will terminate TLS for `sso-lb-a.mydomain.com`. We must install the certificate chain and keys generated by our internal Root CA. 

The `haproxy.cfg` engine expects a single concatenated `.pem` bundle for its frontend bindings. This file must contain the server private key, the public certificate, and the signing CA certificate chain.

1.  Create the secure directory for HAProxy's SSL assets:
    ```sh
    sudo mkdir -p /etc/haproxy/ssl
    ```
2.  Copy your private key (`sso-lb-a.mydomain.com.key`), server certificate (`sso-lb-a.mydomain.com.crt`), and public CA certificate (`lab-root-ca.crt`) to the VM.
3.  Concatenate these files into the single `.pem` bundle:
    ```sh
    sudo cat sso-lb-a.mydomain.com.key \
             sso-lb-a.mydomain.com.crt \
             lab-root-ca.crt \
             > /etc/haproxy/ssl/haproxy.pem
    ```
4.  Copy the public Root CA certificate separately to serve as our trusted CA file (`internal-ca.pem`) for verifying backend Keycloak nodes:
    ```sh
    sudo cp lab-root-ca.crt /etc/haproxy/ssl/internal-ca.pem
    ```
5.  Set strict read-only permissions for the HAProxy process:
    ```sh
    sudo chmod 600 /etc/haproxy/ssl/haproxy.pem
    sudo chmod 644 /etc/haproxy/ssl/internal-ca.pem
    sudo chown -R root:haproxy /etc/haproxy/ssl
    ```

---

### **Step 5: Create the HAProxy Configuration**

Copy the modernized [haproxy-site-local.cfg](../assets/haproxy-site-local.cfg.template) template into `/etc/haproxy/haproxy.cfg` and edit the file to set the correct backend server targets.

```sh
# Copy the template to active configuration path
sudo cp ./assets/haproxy-site-local.cfg.template /etc/haproxy/haproxy.cfg

# Open the file for editing
sudo vi /etc/haproxy/haproxy.cfg
```

#### **The Production-Hardened Backend Design:**
Ensure the backend pool block is configured securely. We enable **`verify required`** to force HAProxy to validate the backend Keycloak nodes' self-signed certificates using our Root CA bundle, and we enforce **`KC_SESSION`** cookie stickiness to avoid redundant cross-site session transfers:

```haproxy
backend keycloak_local_backend
    balance roundrobin
    
    # --- Session Stickiness ---
    # Inspects Keycloak's KC_SESSION cookie to anchor users to a single node
    cookie KC_SESSION prefix nocache

    # --- Health Checks ---
    # Queries Keycloak's dedicated management readiness endpoint on port 9000
    option httpchk GET /health/ready HTTP/1.1\r\nHost:\ sso.mydomain.com\r\n\r\n

    # --- Backend Server Pool ---
    # We verify the backend certificates using our trusted ca-file bundle
    server sso1a sso-1-a.mydomain.com:443 check ssl verify required ca-file /etc/haproxy/ssl/internal-ca.pem cookie sso1a check port 9000 check-ssl verify none inter 2000ms
    server sso2a sso-2-a.mydomain.com:443 check ssl verify required ca-file /etc/haproxy/ssl/internal-ca.pem cookie sso2a check port 9000 check-ssl verify none inter 2000ms
```

---

### **Step 6: Start and Verify**

Enable and start the HAProxy service:

```sh
# Enable the service to start on boot
sudo systemctl enable haproxy

# Start the service
sudo systemctl start haproxy

# Verify the status
sudo systemctl status haproxy
```

---

### **Step 7: Repeat for Site B**

Repeat Steps 1-6 on your `sso-lb-b` load balancer VM:
*   When creating `/etc/haproxy/ssl/haproxy.pem`, concatenate the key and certificate for `sso-lb-b.mydomain.com`.
*   When editing `haproxy.cfg`, update the backend pool with the addresses of your Site B backend nodes: `sso-1-b` and `sso-2-b` (with their corresponding cookies `sso1b` and `sso2b`).

---

### **Verification**

With both load balancers configured and running, you can access your Keycloak environments via their local gateways. Open your browser and navigate to:
*   `https://sso-lb-a.mydomain.com/auth`
*   `https://sso-lb-b.mydomain.com/auth`

Both gateways will terminate TLS, perform health checks on the backend JVM nodes, and serve the Keycloak welcome interface securely. We are now ready to build the global GSLB "brain" to orchestrate failovers between these two sites.
